how it works

one daemon, a thin cli, and the agents you already have. nothing new to learn for them, they call it from the shell like git.

  1. install finds your agents

    it looks for every coding agent on the machine and links one brain folder into each: the skill, an always-on rule, and hooks where the agent supports them. it backs up any file it edits, once, and --dry-run shows the plan first.

  2. agents run it from the shell

    the first call starts one daemon on 127.0.0.1 with a token from your home folder. every other call is a thin client. there's one owner because qenlo locks a collection to one process.

  3. ollama embeds, qenlo searches

    embeddings come from ollama on your gpu (arctic-embed 33m, 58 MB of vram). vectors live in a qenlo collection, text and provenance in sqlite next to it.

  4. every memory has a name on it

    the agent that wrote it is read from the shell (claude code sets AI_AGENT), so a recall says by codex or by cursor and you can tell where an idea came from.

recall looks three ways at once

a 22m or 33m embedding model is small enough to run anywhere, and small enough to blur exactly the things agents remember: names, ports, versions, paths. so recall adds three scores.

meaning
the query's embedding against every current memory, exact search in qenlo, no approximate index.
words
bm25 over sqlite's fts5, which ships with python. it only counts as far as its best hit is real evidence.
time
last week or in september becomes a timestamp window and a second dense search inside it.

0.5 · meaning + 0.5 · words + 0.25 · time

that recipe came out of a closed-loop study of about sixty memory papers. LoCoMo facts recall@5 went from 51.3 to 58.7, and a recency bonus, the obvious other idea, made things worse.

when a fact changes, the old one steps aside

an old port that keeps coming back is worse than no memory at all. in a test with 20 facts that change and 200 distractors, plain append-only memory put the stale value on top 60% of the time.

the agent writing the memory is already an llm, so it can tell when a fact replaced another one. remember shows the memories the new one is probably about, and --replaces links them. the old one leaves search and stays in history. for facts that are made to change, --key staging.db.port names the slot and needs no id. the new value came first 20 out of 20 times.

qenlo-memory remember "the daemon listens on 7438" --replaces 12
qenlo-memory history 12
  1. #12 the daemon listens on 7437, by codex
  2. #52 the daemon listens on 7438, replaces #12
  3. history 12: replaced by #52, still readable

when two notes disagree, both get a label

0.4 left the noticing to the writer. two unlinked notes that disagreed both stayed live, and nothing said which one was current. 0.5 adds the checks that need no model. 0.5.1 closes a race in review: confirm <id> --expect N is refused if a newer disagreement landed while you were reviewing, so you never clear a label on a stale read.

flagged at write
the same word followed by a different value, or a flipped "not" in short notes. the older memory stays live, labelled possibly stale. --strict refuses the write instead.
compare-and-swap
--key K --expect <id you read> saves only if the key still points at that id. otherwise nothing is saved, and you're told the current value and who wrote it.
tentative, then confirmed
--tentative keeps a guess searchable but out of session context. confirm promotes it, and pending lists what's still waiting.
what changed, and checking work
changes --days 7 lists each replaced memory next to its replacement. git diff | qenlo-memory check exits 1 when a diff breaks a stored decision.

it's a flag, not a ruling. the check is tuned to stay quiet: on my real store it flagged 1 of 49 near-duplicate pairs, where the naive version flagged 37, almost all false. it misses contradictions stated in other words, and it misses "always" quietly becoming "usually".

100 agents at once, real daemon and real embeddings

one laptop (rtx 4050, ollama embeddings), on a copy of my store. 0.4 reset 71 of 1,000 simultaneous writes: python's http server kept a backlog of 5 and windows reset the rest. 0.5 raises the backlog to 1,024, shares one sqlite transaction across writers that arrive together, and pools ollama embeds. 1,000 out of 1,000, three runs out of three.

under it, qenloDB

qenlo is the embedded vector database i'm building, in rust. one process owns one durable record store, filters run before ranking, and search is exact. there's no index to tune and no server to run.

indexes are disposable, application data isn't. so ids, vectors, metadata and tombstones live in one canonical store, and the cpu, wgpu, usearch and pytorch paths are structures built from it that can be thrown away and rebuilt. search runs on the cpu by default and moves to the gpu once a matrix is big enough to be worth moving.

sdks for rust, python and typescript, with go, kotlin and swift in preview.

time to first query is 0.64 s, against 48 to 80 s for FAISS HNSW, Chroma and Milvus Lite to build an index. a selective filter with 1% of rows eligible answers in 0.24 ms against Chroma's 43.

where it loses: FAISS HNSW answers the same 100k cell in 1.5 ms, approximate, against qenlo's 12.9 exact, and FAISS on a gpu beat qenlo's cuda prototype at 1M × 768. qenlo is exact and embedded. it isn't the fastest ann engine and doesn't try to be.

what building a product on it taught the database

  • in alpha.10 the write-ahead log only ever grew, because flush() returned early after every commit. qenlo-memory found it, alpha.11 fixed it.
  • an agent's memory is mostly write one thing, then search. up to alpha.11 every write threw away the search matrix. beta.1 keeps each vector once in the buffer search reads, which made add-then-search 13x faster at 2,000 rows and cut memory per row by 40%.

install it in one line

the script installs uv if you don't have it, installs the cli, then qenlo-memory install sets up ollama, pulls the embedding model and wires every agent it finds. then restart your agents. run the same line again to upgrade.

# mac and linux
curl -fsSL https://raw.githubusercontent.com/a3ro-dev/qenlo-memory/main/install.sh | sh

# windows (powershell)
irm https://raw.githubusercontent.com/a3ro-dev/qenlo-memory/main/install.ps1 | iex

then, from any agent or your own shell

qenlo-memory recall "how do we release qenlo"

qenlo-memory remember "staging moved to 6543" --key staging.db.port
qenlo-memory review

good to know

  • runs on windows x64, linux x86_64 and apple silicon. intel macs and linux arm aren't covered yet.
  • qenlo-memory install --dry-run shows every file it would touch without writing anything.
  • it's local and single-user. the daemon only listens on 127.0.0.1 and wants a token from your home folder.
  • secret redaction is a regex for common key formats. it's a seatbelt, not a guarantee.
  • import reads a mem0 export too, if you're moving over.
  • the conflict check is a flag, not a ruling. it misses contradictions stated in other words, and nothing blocks an agent from acting on a stored decision unless you wire check into ci or a hook yourself.
